A program stops in a fault handler, and the debugger shows only registers and addresses. A deep chain of function calls destroys a variable that it never names. An interrupt arrives later than you calculated. To find faults like these, you need to know what the CPU (central processing unit) does with each line of your code. This lesson follows one C statement, `int x = 5;`, from Flash through the CPU into SRAM, and then shows how the stack, the hardware registers and interrupts use the same machine. #CPUArchitecture #MicrocontrollerDesign #EmbeddedHardware

## Von Neumann vs Harvard Architecture

A CPU needs two things from memory: the instructions that say what to do, and the data to do it with. The first design choice is whether both travel on the same road.

### Von Neumann Architecture

In the Von Neumann model, instructions and data share one memory and one bus:

```text
┌─────────┐      ┌───────────────────┐
│         │      │     Memory        │
│   CPU   │══════│  (code + data)    │
│         │      │                   │
└─────────┘      └───────────────────┘
          single bus
```

- The design is simple and needs few wires.
- The CPU cannot fetch an instruction and read data at the same moment. One must wait.
- Most desktop and server processors use it.

### Harvard Architecture

In the Harvard model, instructions and data have separate memories and separate buses:

```text
┌─────────┐      ┌───────────────────┐
│         │══════│  Program Memory   │
│   CPU   │      │  (Flash)          │
│         │══════│  Data Memory      │
│         │      │  (SRAM)           │
└─────────┘      └───────────────────┘
         two separate buses
```

- The CPU can fetch the next instruction while it reads or writes data, so it does more work at the same clock speed.
- Many small microcontrollers use it (AVR, PIC).

### Modified Harvard (ARM Cortex-M)

ARM Cortex-M processors use a mixture: instructions and data have separate buses inside the CPU, but all memory shares one memory map. A switching block, the AHB bus matrix, connects each CPU bus to the memory it asks for. The CPU can fetch an instruction and access data at the same time when they are in different memories.

```text
                   ┌──────────────────┐
                   │   AHB Bus Matrix │
┌──────────┐       │                  │     ┌───────┐
│  Cortex  │═I-bus═│                  │═════│ Flash │
│   -M     │═D-bus═│                  │═════│ SRAM  │
│   CPU    │═S-bus═│                  │═════│Periph │
└──────────┘       └──────────────────┘     └───────┘
```

- **I-bus (Instruction):** fetches instructions from Flash
- **D-bus (Data):** reads constants and other data stored in the code region (Flash)
- **S-bus (System):** reads/writes SRAM and peripherals

So the STM32 can run code from Flash while it reads data from SRAM. When two buses ask for the same memory, the bus matrix makes one of them wait.

## Inside the CPU

<InArticleAd />


### Block Diagram

A CPU has two halves. The first half finds the next instruction and works out what it asks for:

```text
┌─────────┐   ┌───────────┐   ┌─────────┐
│ Program │   │Instruction│   │ Control │
│ Counter │──→│ Register  │──→│  Unit   │
│  (PC)   │   │           │   │         │
└─────────┘   └───────────┘   └────┬────┘
 address of    instruction         │
 the next      in work             ▼
 instruction                 control signals
```

The second half does the work. The control signals choose which registers supply values, what the ALU (arithmetic logic unit) does with them, and where the result goes:

```text
┌─────────────────────────────────┐
│          Register File          │
│ R0  R1  R2 ... R12  SP  LR  PC  │
└───────┬─────────────────▲───────┘
        │ two values      │ result
     ┌──▼──────────────┐  │
     │       ALU       ├──┘
     │ add, sub, AND...│
     └────────┬────────┘
         ┌────▼────┐
         │  Flags  │
         │ N Z C V │
         └─────────┘
```

### Program Counter (PC)

The Program Counter holds the address of the next instruction to fetch. After each fetch, the PC increases to point to the instruction that follows.

On ARM Cortex-M, the PC is register R15. If an instruction reads the PC, it gets its own address plus 4, because the CPU has already fetched ahead.

Branch instructions (`B`, `BL`, `BX`) write a new address into the PC, so execution continues at a different place. This is how `if`, `while` and function calls work in hardware.

### Instruction Register and Decoder

The instruction fetched from Flash is placed in the Instruction Register. An instruction is only a binary number. The Control Unit decodes it to find:

- the operation (add, subtract, load, store, branch)
- the registers that hold the inputs and receive the result
- whether memory must be read or written

The decoder is a combinational logic circuit, built from gates like any other decoder. Its inputs are the bits of the instruction, and its outputs are the control signals for the ALU, the register file and the buses.

### Register File

The register file is a small, fast memory inside the CPU. The CPU works on values here, because memory is slower to reach. ARM Cortex-M3 has 16 core 32-bit registers (13 general-purpose registers plus SP, LR, and PC):

| Register | Name | Purpose |
|----------|------|---------|
| R0-R3 | Arguments/results | Function parameters and return values |
| R4-R11 | General purpose | Callee-saved (preserved across function calls) |
| R12 | IP | Intra-procedure scratch register |
| R13 | SP | Stack Pointer |
| R14 | LR | Link Register (return address for function calls) |
| R15 | PC | Program Counter |

Each register is a row of 32 flip-flops that load together. In one clock cycle, the register file can supply two input values and accept one result.

### Arithmetic Logic Unit (ALU)

The ALU does the arithmetic and the logic. It takes two inputs from the register file and produces one output and the status flags.

| Category | Operations | Built From |
|----------|-----------|-----------|
| Arithmetic | ADD, SUB, MUL | Adders, subtractors |
| Logic | AND, OR, XOR, NOT | Logic gates |
| Shift | LSL, LSR, ASR, ROR | Multiplexers (a barrel shifter) |
| Compare | CMP (subtract without storing result) | Adder + flag logic |

The ALU is one large combinational circuit: adders and gate networks work out the results, and multiplexers select the one that the instruction asks for.

### Status Flags

A program must make decisions, and a decision needs a fact about the last result. The ALU records four such facts, the condition flags, after an operation:

| Flag | Name | Set When |
|------|------|----------|
| N | Negative | Result is negative (MSB = 1) |
| Z | Zero | Result is zero |
| C | Carry | Unsigned overflow (carry out of MSB) |
| V | Overflow | Signed overflow (result does not fit in signed range) |

Conditional branch instructions (`BEQ`, `BNE`, `BCS`, `BCC`) test these flags and branch or do not branch. This is how `if (x == 0)` works: the compiler generates a compare instruction, which sets the flags, and then a conditional branch.

## The Instruction Execution Cycle

<InArticleAd />


### Fetch-Decode-Execute

A cook who follows a recipe reads one line, understands it, does it, and moves to the next line. A CPU treats every instruction the same way, in three stages:

<Steps>
1. **Fetch:** The CPU puts the PC value on the address bus, reads the instruction from Flash memory, and stores it in the instruction register. The PC increments.

2. **Decode:** The control unit examines the instruction bits and generates control signals. It determines which ALU operation to perform, which registers to read, and where to store the result.

3. **Execute:** The ALU performs the operation. The result is written to the destination register (or to memory via the data bus).
</Steps>

### Pipelining

The three stages use different parts of the CPU, so they can work on three instructions at once, as the stations of an assembly line do. While one instruction executes, the next is decoded, and the one after that is fetched. This is pipelining:

```text
Clock:    1     2     3     4     5     6
Instr 1: Fetch Decode Execute
Instr 2:       Fetch  Decode Execute
Instr 3:              Fetch  Decode Execute
Instr 4:                     Fetch  Decode Execute
```

The ARM Cortex-M3 has a 3-stage pipeline. Each instruction still takes three cycles, but after the first three cycles one instruction finishes in every clock cycle.

**The cost of a branch:** When a branch changes the PC, the two instructions behind it in the pipeline were fetched from the wrong address. They are thrown away, and the pipeline fills again. This is a pipeline flush, and it wastes 2 clock cycles on Cortex-M3. So code with many taken branches runs slower than code that runs straight on.

## What Happens When You Write `int x = 5;`

<InArticleAd />


Follow this C statement from source code to hardware.

### Step 1: Compilation

The CPU does not understand C. The compiler translates `int x = 5;` into instructions that the CPU has, written here in assembly, the readable form of those instructions. If `x` is a local variable:

```asm
MOV R0, #5      ; Load the immediate value 5 into register R0
STR R0, [SP, #4] ; Store R0 to the stack (SRAM) at offset 4 from SP
```

### Step 2: Assembly to Machine Code

The assembler converts each instruction to the binary number that the CPU decodes, the machine code. Thumb and Thumb-2 are the names of the 16-bit and 32-bit instruction formats of Cortex-M:

```
MOV R0, #5    →  0xF04F 0x0005   (Thumb-2 encoding)
STR R0, [SP, #4] →  0x9001       (Thumb encoding)
```

These binary values are stored in Flash memory. (A compiler will often choose the shorter 16-bit form `MOVS R0, #5`, which is `0x2005`. The steps below are the same.)

### Step 3: Fetch

The CPU places the PC value (say, `0x08000100`) on the I-bus address lines. The Flash controller responds with the instruction word `0xF04F0005`. The instruction register captures it.

### Step 4: Decode

The control unit decodes `0xF04F0005` as "MOV R0, #5":

- Operation: move an immediate value (a number written inside the instruction) to a register
- Destination: R0
- Immediate value: 5

It then sets the control signals that:

- send the immediate value (5) to the ALU input
- tell the ALU to pass its input through unchanged
- enable writing to R0 in the register file

### Step 5: Execute

The ALU receives the value 5 and passes it through. On the next clock edge, the D flip-flops of R0 capture it.

### Step 6: Store to SRAM

The next instruction (`STR R0, [SP, #4]`) stores the value in R0 to SRAM:

- The CPU calculates the address: SP + 4 (stack pointer plus offset)
- The address goes on the S-bus address lines
- The value in R0 (5) goes on the S-bus data lines
- The write control signal becomes active
- The SRAM at that address stores the value

The variable `x` is now the value 5 in one SRAM location, at address `SP + 4`. The name `x` exists only in your source code.

## The Stack

<InArticleAd />


### What Is the Stack?

Every function call needs some memory for a short time, and gives it back when it returns. The stack is the region of SRAM that lends this memory. It works like a pile of plates: the last plate put on is the first one taken off. A function puts three things on it:

- its local variables, which exist only while the function runs
- the return address: the instruction to continue with after the call
- the old values of registers that it must give back unchanged

### How the Stack Works

The Stack Pointer (SP, R13) holds the address of the top of the stack. On ARM Cortex-M the stack grows downward, toward lower addresses:

```text
High address    ┌──────────────┐
                │              │  (used by the caller)
                │              │
                ├──────────────┤ ← SP (on entry)  
                │  Saved LR    │
                ├──────────────┤
                │  Saved R4    │
                ├──────────────┤
                │  Local var x │
                ├──────────────┤
                │  Local var y │
                ├──────────────┤ ← SP (current)
                │              │  (free stack space)
Low address     └──────────────┘
```

**PUSH** decrements SP and stores a value. **POP** loads a value and increments SP.

### Stack Overflow

Nothing stops the stack at the end of its region. If it grows too large (deep recursion, large local arrays), it writes over other data in SRAM. This is a stack overflow. The program may crash, or it may continue with wrong data and give no sign. On an MCU with little SRAM (2 KB on the ATmega328P) it happens easily.

**Check it: measure the stack, do not guess it.** At start-up, fill the free stack area with a known pattern such as `0xA5`. Run the device through its heaviest work (every interrupt, the deepest call), then read the area with the debugger. The bytes that still hold `0xA5` were never used. Keep a margin of a few hundred bytes; if the pattern is gone to the end of the area, the stack has already overflowed.

## Memory-Mapped I/O

<InArticleAd />


### The Key Insight

The CPU has no instruction that means "set a pin high". On ARM Cortex-M (and most modern MCUs) it does not need one. The registers of each peripheral, the hardware blocks such as timers and pin drivers, have addresses in the memory map, as SRAM locations have. The CPU reaches them with the same load and store instructions.

```c
// Writing to SRAM (a variable)
volatile uint32_t *sram_addr = (volatile uint32_t *)0x20000000;
*sram_addr = 42;

// Writing to a GPIO register (identical syntax)
volatile uint32_t *gpio_odr = (volatile uint32_t *)0x4001080C;
*gpio_odr = 0x0001;
```

To the CPU these two operations are the same. It puts the address on the bus, and the address decoder sends the data to SRAM or to the GPIO (general purpose input/output) peripheral.

### How Writing to a Register Controls Hardware

When you write `GPIOA->ODR = 0x0001;`:

<Steps>
1. The compiler generates a STR instruction to address `0x4001080C`.
2. The CPU places `0x4001080C` on the address bus.
3. The AHB bus matrix routes the transaction to APB2 (where GPIO lives).
4. The address decoder enables GPIOA.
5. Within GPIOA, the offset `0x0C` selects the ODR (Output Data Register).
6. The data `0x0001` is latched into the ODR register (a set of D flip-flops).
7. Bit 0 of the ODR drives the output buffer of pin PA0.
8. PA0 goes high (3.3V on the physical pin).
</Steps>

Two earlier writes must have been made, or nothing happens. The clock of GPIOA must be switched on (bit IOPAEN in the RCC register `RCC->APB2ENR`): a peripheral without its clock ignores every write, with no error. And PA0 must be set up as an output in `GPIOA->CRL`. When a pin "does nothing", check these two before the wiring.

## Interrupts and the Vector Table

<InArticleAd />


### Why Interrupts?

To know that a visitor has arrived, you can walk to the door every minute and look, or you can fit a doorbell and continue your work. Looking again and again is polling: a loop that tests a condition, and wastes CPU time. The doorbell is an interrupt: a hardware event pauses the running code, the CPU runs a short function for the event (the handler), and then it returns to the paused code.

```c
// Polling (wastes CPU time)
while (!(USART1->SR & (1 << 5))) { }  // Wait for RXNE flag
uint8_t data = USART1->DR;

// Interrupt (CPU does other work until data arrives)
void USART1_IRQHandler(void) {
    uint8_t data = USART1->DR;  // Called automatically when data arrives
    // store data in a volatile buffer here, for the main loop to read
}
```

### How Interrupts Work in Hardware

<Steps>
1. **Event occurs:** A peripheral (timer overflow, UART receive, GPIO edge) sets an interrupt request flag.

2. **NVIC arbitration:** The NVIC (Nested Vectored Interrupt Controller) compares the priority of the new interrupt with the priority of the code that is running. If the new interrupt has higher priority, it proceeds.

3. **Context save:** The paused code must find its values unchanged when it continues. So the CPU pushes R0-R3, R12, LR, PC, and xPSR (the register that holds the flags) onto the stack. On Cortex-M the hardware does this by itself, in 12 clock cycles.

4. **Vector fetch:** The CPU reads the address of the handler function from the interrupt vector table.

5. **Handler execution:** The CPU jumps to the handler function and executes it.

6. **Context restore:** When the handler returns, the CPU pops the saved registers from the stack and continues the paused code.
</Steps>

### The Vector Table

The CPU must know where the handler of each interrupt is. The vector table is a list of 32-bit addresses, one for each interrupt, in a fixed order. It is stored at the beginning of Flash (address `0x08000000` on STM32):

| Offset | Vector | Description |
|--------|--------|-------------|
| 0x0000 | Initial SP | Stack pointer value loaded at reset |
| 0x0004 | Reset | Address of the reset handler (entry point) |
| 0x0008 | NMI | Non-Maskable Interrupt handler |
| 0x000C | HardFault | Hardware fault handler |
| ... | ... | ... |
| 0x00B0 | TIM2 | Timer 2 interrupt handler |
| 0x00D4 | USART1 | USART1 interrupt handler |
| ... | ... | ... |

When the MCU powers on, it reads the initial SP from offset 0x0000 and the address of the reset handler from offset 0x0004, and starts there. So the vector table must be at exactly this address. The linker script, the file that tells the build tools where each part of the program goes, places it there.

### Interrupt Latency

Latency is the time from the event to the first instruction of the handler. On ARM Cortex-M3 it is 12 clock cycles when no other handler is in the way. At 72 MHz, that is $12 / 72\text{ MHz} \approx 167\text{ ns}$. Because this time is known in advance, Cortex-M suits real-time work.

The 12 cycles are the best case. An interrupt arrives later than this when:

- a handler of the same or higher priority is running, and the new one must wait until it returns;
- the program has turned interrupts off (`__disable_irq()`) around a critical part;
- the memory is slow: at 72 MHz the STM32F103 Flash needs 2 wait states, so the vector fetch and the first instructions take extra cycles.

So the worst case is the longest handler of higher priority, plus the longest time interrupts are off, plus the 12 cycles. That is the number to compare with your deadline.

## Exercises

<InArticleAd />


### Exercise 1: Instruction Trace

The following ARM assembly code executes. Trace the register values after each instruction:

```asm
MOV R0, #10     ; R0 = ?
MOV R1, #3      ; R1 = ?
ADD R2, R0, R1  ; R2 = ?
SUB R3, R0, R1  ; R3 = ?
AND R4, R0, R1  ; R4 = ?
```

<details>
<summary>**Solution**</summary>

| Instruction | R0 | R1 | R2 | R3 | R4 |
|------------|----|----|----|----|-----|
| MOV R0, #10 | 10 | - | - | - | - |
| MOV R1, #3 | 10 | 3 | - | - | - |
| ADD R2, R0, R1 | 10 | 3 | 13 | - | - |
| SUB R3, R0, R1 | 10 | 3 | 13 | 7 | - |
| AND R4, R0, R1 | 10 | 3 | 13 | 7 | 2 |

For AND: 10 = `1010`, 3 = `0011`, AND = `0010` = 2.

</details>

### Exercise 2: Memory-Mapped I/O

On an STM32F103, GPIOB base address is `0x40010C00`. The ODR offset is `0x0C`. Write a C expression that sets pin PB5 high without changing other pins.

<details>
<summary>**Solution**</summary>

```c
volatile uint32_t *gpiob_odr = (volatile uint32_t *)(0x40010C00 + 0x0C);
*gpiob_odr |= (1 << 5);
```

Or using the CMSIS/HAL headers:

```c
GPIOB->ODR |= (1 << 5);
```

The `|=` (OR) operation sets bit 5 without changing other bits. The address `0x40010C0C` routes through the bus matrix to APB2, then to the GPIOB peripheral, then to the ODR register.

</details>

### Exercise 3: Stack Depth

A function `foo()` has 3 local `uint32_t` variables and calls `bar()`, which has 2 local `uint32_t` variables. Ignoring saved registers and alignment padding, how many bytes of stack space do these two functions use together?

<details>
<summary>**Solution**</summary>

`foo()`: $3 \times 4 = 12$ bytes.

`bar()`: $2 \times 4 = 8$ bytes.

Total stack depth when `bar()` is executing (called from `foo()`): $12 + 8 = 20$ bytes.

In practice, the compiler also saves the return address (LR) in `foo()`, may push callee-saved registers, and adds padding for alignment, so the actual usage is somewhat more.

</details>

### Exercise 4: Interrupt Priority

Two interrupts fire simultaneously: TIM2 (priority 2) and USART1 (priority 1). On Cortex-M, lower priority numbers mean higher priority. Which handler executes first?

<details>
<summary>**Solution**</summary>

USART1 (priority 1) executes first because it has a lower priority number, meaning higher priority. TIM2 (priority 2) stays pending and is serviced after USART1's handler returns. A lower-priority interrupt never preempts a higher-priority handler.

</details>

## Putting It All Together

<InArticleAd />


The whole microcontroller is a CPU, two memories and a set of peripherals on one bus system:

```text
  ┌─────────────────────────────────────┐
  │  ┌───────┐   ┌───────┐  ┌───────┐   │
  │  │  CPU  │   │ Flash │  │ SRAM  │   │
  │  │Cortex │◄═►│ code  │  │ data  │   │
  │  │  -M   │   │ 64 KB │  │ 20 KB │   │
  │  └───┬───┘   └───────┘  └───────┘   │
  │      │   AHB / APB bus              │
  │  ════╪═══════════════════════════   │
  │  ┌───┴──┐ ┌─────┐ ┌────┐ ┌─────┐    │
  │  │ GPIO │ │Timer│ │ADC │ │SPI  │    │
  │  │ports │ │ PWM │ │    │ │I2C  │    │
  │  │      │ │     │ │    │ │UART │    │
  │  └──┬───┘ └──┬──┘ └─┬──┘ └──┬──┘    │
  └─────┼────────┼──────┼───────┼───────┘
     pins     pins   analog   serial
                      pins    pins
```

Every topic of this course is a part of it:

| Topic | Where it is in the MCU |
|--------------|---------------|
| Binary and hex | Every register value, every address |
| Logic gates | ALU operations, decoder logic, multiplexers |
| Combinational logic | Address decoders, ALU arithmetic, GPIO mux |
| Flip-flops and registers | CPU register file, SPI shift registers, peripheral registers |
| Counters and timers | Timer peripherals, prescalers, PWM generators |
| Memory | Flash (program), SRAM (variables), memory-mapped peripherals |
| Buses and interfaces | AHB/APB internal buses, SPI/I2C/UART peripherals |
| ADC and DAC | ADC peripheral, PWM output (pseudo-DAC) |
